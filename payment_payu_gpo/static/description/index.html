Payment Provider: PayU GPO

Payment provider for PayU GPO (Europe, secure.payu.com, REST API v2.1). Not to be confused with PayU India (payu.in).

  • Hosted payment page (redirect) for BLIK and other non-card methods.
  • Card payments through the PayU Secure Form, with card tokenization: the first payment is sent with recurring: FIRST; once COMPLETED, the multi-use TOKC_ token is stored as a payment.token.
  • Merchant-initiated charges: _send_payment_request() charges the token with recurring: STANDARD, so any off-session charge (cron, subscription) works with the standard payment API.
  • When the card of a completed payment cannot be read from PayU (e.g. after 3DS), an hourly cron retries saving it for three days.
  • Signed notifications (OpenPayu-Signature, POS second key) for orders and refunds.
  • Partial and full refunds.

Important

This is an alpha version, the data model and design can change at any time without warning. Only for development or testing purpose, do not use in production. More details on development status

Configuration

Create one provider per company in Accounting > Configuration > Payment Providers and fill in the POS id, the OAuth client_id / client_secret and the second key from the PayU merchant panel. State Test uses the sandbox (secure.snd.payu.com).

PayU must enable recurring payments on the POS (cards), and the trusted_merchant grant used to list the buyer’s card tokens.

PayU must reach the notification URL. When Odoo’s base URL is not public (reverse proxy, development behind a tunnel), set the system parameter payment_payu_gpo.notify_base_url to the public URL that forwards /payment/payu_gpo/webhook to Odoo; the buyer still returns to the base URL.

Behind a reverse proxy, run Odoo with proxy_mode = True: the buyer’s IP address is sent to PayU with card payments (3-D Secure, fraud checks).

Known issues / Roadmap

  • Validate the notification payloads (order, refund) against production data.
  • BLIK recurring (PAYID token, model “O”, 2000 PLN cap) needs a contract annex with PayU; it is Poland-specific and belongs in a separate module.
  • PayU does not retry declined merchant-initiated charges: the retry policy is left to the calling module.
  • Odoo 19/20 port: payu_client.py has no Odoo import. The _payu_gpo_* helpers of payment.transaction map one-to-one onto the Odoo 19/20 hooks _extract_reference, _apply_updates and _extract_token_values. Odoo 20 also forbids direct write() on transactions outside payment_safe_write / _record().
