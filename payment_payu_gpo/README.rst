Payment provider for **PayU GPO** (Europe, ``secure.payu.com``, REST API
v2.1). Not to be confused with PayU India (``payu.in``).

- Hosted payment page (redirect) for BLIK and other non-card methods.
- Card payments through the PayU Secure Form, with a "Name on card"
  field next to it (the Secure Form asks none): sent to PayU as 3-D
  Secure cardholder data and as the buyer's name, so the payer's name
  comes back in PayU's notification.
- Card tokenization: a card saved on payment is a card on file
  (``cardOnFile: FIRST``), or a card for scheduled recurring charges
  (``recurring: FIRST``) when ``_payu_gpo_card_is_recurring()`` says so.
  The multi-use ``TOKC_`` token PayU returns with the order is saved as
  a ``payment.token`` once the order is ``COMPLETED``.
- Merchant-initiated charges: ``_send_payment_request()`` charges the
  token without the buyer (``recurring: STANDARD``, or
  ``cardOnFile: STANDARD_MERCHANT``), so any off-session charge (cron,
  subscription) works with the standard payment API. A charge the bank
  refuses (PayU cancels the order, or asks for the cardholder) is set to
  error, not cancelled: nobody gave it up.
- A request PayU did not answer (timeout, 5xx), or answered in a way
  that can't be used, leaves the payment pending with any PayU id it
  gave: the order may exist, and its notification or a status read
  settles it. A hosted-page payment whose page PayU did not return is
  set to error at once instead: the buyer never reached PayU, so nothing
  was paid. A payment or refund PayU never confirms (no PayU id, no
  notification) is set to error after four days, once PayU has stopped
  retrying its notifications (72 hours), and flagged
  ``payu_gpo_unconfirmed``: its outcome is unknown, which is not a
  refusal. A final answer from PayU that still comes clears the flag:
  the payment is then done, or stays in error as a certain refusal.
- When the card of a completed payment cannot be read from PayU, an
  hourly cron retries saving it for three days.
- When PayU's notification of a payment is lost (Odoo down or not
  reachable), a cron reads the status of the payments still pending
  every 15 minutes, for two days, and the payment status page reads it
  while the buyer waits.
- Signed notifications (``OpenPayu-Signature``, POS second key) for
  orders and refunds, checked against the payment (PayU order, amount,
  currency). Data that does not match, from a notification or a status
  read, is not applied: the payment stays pending, with the discrepancy
  on it and in the log.
- Partial and full refunds.

Configuration
=============

Create one provider per company in *Accounting > Configuration > Payment
Providers* and fill in the POS id, the OAuth ``client_id`` /
``client_secret`` and the second key from the PayU merchant panel. State
*Test* uses the sandbox (``secure.snd.payu.com``).

PayU must enable on the POS:

- **automatic collection** (auto-receive) for every payment method: the
  module does not capture payments, and PayU cancels an uncaptured one
  (``WAITING_FOR_CONFIRMATION``) after a few days;
- **card tokens**: recurring payments (``recurring``) and/or cards on
  file (``cardOnFile``), and the ``trusted_merchant`` grant used to list
  the buyer's card tokens.

PayU must reach the notification URL. When Odoo's base URL is not public
(reverse proxy, development behind a tunnel), set the system parameter
``payment_payu_gpo.notify_base_url`` to the public URL that forwards
``/payment/payu_gpo/webhook`` to Odoo; the buyer still returns to the
base URL.

Behind a reverse proxy, run Odoo with ``proxy_mode = True``: the buyer's
IP address is sent to PayU with card payments (3-D Secure, fraud
checks).

A neutralized copy of the database (``odoo-bin neutralize``) has its
PayU keys wiped, and a disabled provider never calls PayU.

Known issues / Roadmap
======================

- Validate the notification payloads (order, refund) against production
  data.
- Not supported yet:

  - saving a card without paying (card validation): PayU needs a
    zero-amount order, enabled on a POS on request;
  - paying with a saved card while the buyer is on the site
    (``cardOnFile: STANDARD_CARDHOLDER`` and the 3DS / CVV redirects):
    saved PayU cards are only charged without the buyer;
  - the CVV that PayU may ask for a card (``WARNING_CONTINUE_CVV``,
    through the Secure Form ``sendCvv``): the payment is refused with a
    clear message;
  - manual capture (``WAITING_FOR_CONFIRMATION``, ``authorized`` state);
  - refunds made in the PayU panel, and reading the status of a refund
    whose notification was lost.

- BLIK recurring (PAYID token, model "O", 2000 PLN cap) needs a contract
  annex with PayU; it is Poland-specific and belongs in a separate
  module.
- PayU does not retry declined merchant-initiated charges: the retry
  policy is left to the calling module.
- Odoo 19/20 port: ``payu_client.py`` has no Odoo import. The
  ``_payu_gpo_*`` helpers of ``payment.transaction`` map one-to-one onto
  the Odoo 19/20 hooks ``_extract_reference``, ``_apply_updates`` and
  ``_extract_token_values``. Odoo 20 also forbids direct ``write()`` on
  transactions outside ``payment_safe_write`` / ``_record()``.
